Animated walkthroughOne request through Spring MVC — filters, DispatcherServlet, and where errors go

1 · Happy path

  1. POST /api/orders arrives. Servlet filters run first, outside Spring MVC: Spring Security, correlation id / MDC, request logging. Any of them can end the request here.
  2. DispatcherServlet asks RequestMappingHandlerMapping for a handler. It matches path, method, consumes and produces and returns the controller method plus its interceptors.
  3. Each HandlerInterceptor's preHandle() runs. Unlike a filter it already knows the chosen handler method, and returning false stops the request (Interview Problem 6's rate limiter works this way).
  4. The HandlerAdapter resolves each parameter. @RequestBody reads the JSON with an HttpMessageConverter (Jackson), then @Valid runs Bean Validation.
  5. Your controller method runs with fully built, validated arguments. There's no HTTP parsing in your code.
  6. The returned ResponseEntity<OrderResponse> is written as JSON by a message converter, chosen by content negotiation against Accept. ResponseBodyAdvice can adjust the body here.
  7. postHandle() then afterCompletion() run on the way out. With @ResponseBody the body is already written, so postHandle() can't change it; use afterCompletion() for timing and cleanup.
  8. The response passes back out through the filters, in reverse order, to the client: 201 Created.

2 · Validation fails

  1. Same request, but the body has "quantity": 0. Filters, handler mapping and preHandle() run exactly as before.
  2. @Valid fails while the argument is being resolved, so Spring throws MethodArgumentNotValidException. Your controller method never runs.
  3. The exception goes to the HandlerExceptionResolvers. ExceptionHandlerExceptionResolver finds the matching @ExceptionHandler in your @ControllerAdvice (Chapter 10).
  4. The handler returns a ProblemDetail, written as application/problem+json with status 400 and the field errors.
  5. postHandle() is skipped, but afterCompletion() still runs. The 400 travels back out through the filters.

3 · Rejected by a filter

  1. No valid token. Spring Security's filter answers 401 on its own; DispatcherServlet is never called.
  2. So no interceptor, @ControllerAdvice or controller code runs, and your ProblemDetail handler can't shape this error. Filter-level errors need their own handling (Chapter 17's AuthenticationEntryPoint).
