Animated walkthroughPropagation in motion — REQUIRED, the rollback-only trap, REQUIRES_NEW, NESTED

1 · REQUIRED joins

  1. importAll() is @Transactional, so its own proxy already began tx1 on connection #1. It loops over rows and calls importer.importRow(row).
  2. The call reaches RowImporter's proxy. importRow() uses the default propagation, REQUIRED.
  3. A transaction is already bound to the thread, so REQUIRED joins it. No new transaction and no new connection: the row's INSERT runs in tx1.
  4. importRow() returns. A joined call never commits by itself; only the boundary that started the transaction does.
  5. importAll() finishes and its proxy commits tx1 once, covering every row, then returns connection #1 to the pool.

2 · The rollback-only trap

  1. Same setup as §5.2, but this row is invalid. importRow() joins tx1 and throws a RuntimeException.
  2. The inner proxy didn't start tx1, so it can't roll it back. It marks the shared transaction rollback-only and rethrows.
  3. importAll() catches the exception, counts the row as failed and carries on. The flag stays set: catching an exception doesn't clear it.
  4. At the end the outer proxy tries to commit. The transaction is rollback-only, so Spring rolls back everything, good rows included, and throws UnexpectedRollbackException.

3 · REQUIRES_NEW

  1. Fix A from §5.2: importRow() uses REQUIRES_NEW. importAll() calls it while tx1 is active.
  2. The interceptor suspends tx1 (unbinds it from the thread) and begins tx2 on a second connection. tx1 keeps holding connection #1 while it waits.
  3. The bad row throws. Only tx2 rolls back, and connection #2 goes back to the pool. Good rows each committed in their own tx2.
  4. tx1 resumes. importAll() catches the exception, and this time tx1 was never marked rollback-only.
  5. tx1 commits normally. The cost is in the pool panel: every REQUIRES_NEW level holds a second connection, and under load a pool can deadlock itself.

4 · NESTED

  1. With NESTED, importRow() stays inside tx1 but behind a savepoint.
  2. The interceptor runs SAVEPOINT SP1 on connection #1. Same transaction, same connection: the pool isn't touched.
  3. The row fails: ROLLBACK TO SAVEPOINT SP1 undoes just this row's work, and tx1 is not marked rollback-only.
  4. importAll() catches the exception and moves on to the next row.
  5. tx1 commits every good row in one transaction on one connection. The catch: savepoints roll back the JDBC connection, not JPA's persistence context, which is why NESTED is meant for JDBC code.
