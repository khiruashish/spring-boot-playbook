Animated walkthroughThrough the security filter chain — 200, 401 and 403

1 · Valid JWT

  1. Spring Security is a single servlet filter, DelegatingFilterProxy, which hands the request to FilterChainProxy.
  2. FilterChainProxy picks the first SecurityFilterChain whose matcher fits. /api/orders matches the stateless /api/** chain, and only that chain's filters run.
  3. SecurityContextHolderFilter sets up an empty SecurityContext for this thread. Header, CORS and CSRF filters follow; a stateless token API usually disables CSRF.
  4. BearerTokenAuthenticationFilter finds Authorization: Bearer …. (An invalid or expired token fails right here, with a 401.)
  5. JwtDecoder checks the signature against the cached JWK set, then exp, issuer and audience. JwtAuthenticationConverter maps claims to authorities such as ROLE_CUSTOMER.
  6. The authenticated token is stored in the SecurityContext, so later filters and your code (@AuthenticationPrincipal, @PreAuthorize) can see who is calling.
  7. AnonymousAuthenticationFilter has nothing to do, because a user is already authenticated.
  8. ExceptionTranslationFilter wraps the rest of the chain to catch security exceptions. AuthorizationFilter checks the rule for /api/orders (authenticated()): granted.
  9. The request reaches DispatcherServlet and your controller, which is the Spring MVC flow from Chapter 8.

2 · No token → 401

  1. GET /api/orders again, but with no Authorization header. BearerTokenAuthenticationFilter finds no token and passes the request on. A missing token isn't an error yet.
  2. AnonymousAuthenticationFilter fills the empty context with an AnonymousAuthenticationToken.
  3. AuthorizationFilter: /api/orders needs an authenticated user, so it throws AccessDeniedException.
  4. ExceptionTranslationFilter catches it. The caller is anonymous, so this is really an authentication problem…
  5. …so it starts authentication through the AuthenticationEntryPoint: 401 with WWW-Authenticate: Bearer.
  6. The 401 goes straight back. DispatcherServlet and @ControllerAdvice never ran, which is why §3.3 configures the entry point to write a ProblemDetail.

3 · Wrong role → 403

  1. A customer with a valid token calls GET /api/admin/reports. Authentication succeeds exactly as in scene 1: ROLE_CUSTOMER.
  2. AuthorizationFilter: /api/admin/** requires hasRole("OPS"), meaning the authority ROLE_OPS. Denied, with AccessDeniedException.
  3. ExceptionTranslationFilter catches it. This time the caller is authenticated, so it's a genuine authorization failure…
  4. …handled by the AccessDeniedHandler: 403 Forbidden.
  5. Again, nothing in Spring MVC ran. Method-level @PreAuthorize denials are different: they happen inside the controller call, so @ControllerAdvice can handle them.
