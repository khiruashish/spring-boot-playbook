Animated walkthroughBackpressure — demand flows up, data flows down

1 · Demand drives the source

  1. The client subscribes and demand travels upstream as request(n). Netty keeps asking while the socket can take data, and limitRate(100) turns that into requests for 100 rows at a time.
  2. Rows flow down only as fast as they were requested. Nothing is pushed that nobody asked for.
  3. The mobile client reads slowly, so the TCP send buffer fills up…
  4. …and Netty stops requesting. Rows already requested arrive and wait, but no new demand goes upstream.
  5. So the source simply pauses: the database cursor isn't read any further and memory stays flat. For a paged export, that's exactly what you want.
  6. When the client catches up, demand resumes and so does the source.

2 · A push source (live feed)

  1. Rider positions come from Redis pub/sub: a push source that can't be paused. Positions keep arriving whether or not anyone asked.
  2. With a slow client and no strategy, they would pile up in a buffer per connection: a memory leak with extra steps.
  3. onBackpressureDrop() discards positions nobody has asked for (and counts them in a metric). For live data, only the newest value matters anyway.
  4. sample(2s) sends at most one position every two seconds, so the client always gets a recent position and nothing piles up. Financial events are different: never drop them; persist and let clients replay.
