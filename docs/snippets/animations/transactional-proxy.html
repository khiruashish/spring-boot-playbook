Animated walkthroughThe @Transactional proxy — and how this.method() escapes it

1 · Through the proxy

  1. Spring injected a proxy, not your class. The caller's transferService.transfer() lands in the proxy first.
  2. TransactionInterceptor finds @Transactional on transfer() and asks the PlatformTransactionManager for a transaction: BEGIN tx1, with the connection bound to the current thread.
  3. proceed() calls the real transfer() on the target object. The debit and the credit run on tx1's connection.
  4. The method returns normally, so the interceptor commits tx1 on the way out. An unchecked exception would have rolled it back instead.

2 · The self-invocation trap

  1. Same entry through the proxy. This time transfer() also calls this.audit(), which is annotated @Transactional(REQUIRES_NEW).
  2. The interceptor begins tx1 and calls the real transfer().
  3. this.audit() is a plain Java call on the target object. It never leaves the bean, so no interceptor runs: the dashed route back through the proxy never happens. REQUIRES_NEW is ignored and the audit row is written inside tx1.
  4. Back in transfer(), the debit finds insufficient funds and throws a RuntimeException.
  5. The interceptor sees the exception and rolls back tx1. The audit row disappears along with the debit, which is the opposite of what REQUIRES_NEW promised.

3 · The fix: call another bean

  1. Move the audit logic into its own bean, AuditService.record(), and inject it into TransferService. (A self-injected proxy or a TransactionTemplate also work, but a separate bean is the clearest.)
  2. The interceptor begins tx1 and calls the real transfer().
  3. auditService.record() targets a different bean, so the call goes through its proxy. REQUIRES_NEW now takes effect: tx1 is suspended and tx2 begins on a separate connection.
  4. record() inserts the audit row inside tx2.
  5. On return, the audit proxy commits tx2 and resumes tx1. The audit row is now durable.
  6. transfer() throws, and tx1 rolls back the debit. The audit row survives because tx2 already committed. This is exactly what the REQUIRES_NEW test in Interview Problem 7 asserts.
