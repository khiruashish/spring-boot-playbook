Animated walkthroughHow Boot decides — JdbcTemplateAutoConfiguration through the selection pipeline

1 · Boot's default

  1. Your own @Configuration classes and scanned components are registered first. In this app none of them defines a JdbcTemplate.
  2. AutoConfigurationImportSelector reads every AutoConfiguration.imports file on the classpath: hundreds of candidates.
  3. Exclusions are removed: @SpringBootApplication(exclude = …) and spring.autoconfigure.exclude.
  4. A fast pre-filter reads spring-autoconfigure-metadata.properties and drops candidates whose @ConditionalOnClass can't match, without loading them.
  5. Survivors are sorted by @AutoConfiguration(before/after). JdbcTemplateAutoConfiguration runs after DataSourceAutoConfiguration, so a DataSource already exists.
  6. Full evaluation of the class: JdbcTemplate is on the classpath ✓, and there is exactly one DataSource ✓.
  7. Then the @Bean method's own condition: is there already a JdbcOperations bean? No, so @ConditionalOnMissingBean matches.
  8. Boot registers its JdbcTemplate, configured from spring.jdbc.template.* properties.
  9. Every decision is recorded. Run with --debug or open /actuator/conditions to see positive and negative matches, each with its reason.

2 · Your bean wins

  1. This time your @Configuration declares its own JdbcTemplate (say, with a custom fetch size). It's registered first.
  2. The auto-configuration import is a DeferredImportSelector, so it runs only after all of your configuration…
  3. …and the class-level conditions still match.
  4. But @ConditionalOnMissingBean(JdbcOperations.class) finds your bean, so Boot backs off and its default is never created. The golden rule: your beans win.
  5. The report lists this as a negative match, found beans of type JdbcOperations. It's the first place to look when Boot seems to ignore a default.

3 · Library not on the classpath

  1. Now spring-jdbc isn't on the classpath (say, a WebFlux service using R2DBC). JdbcTemplateAutoConfiguration is still listed in Boot's imports file.
  2. The pre-filter sees that @ConditionalOnClass(JdbcTemplate.class) can't match and drops the candidate before the class is loaded. That's why a class referring to JdbcTemplate doesn't cause a ClassNotFoundException.
  3. It still shows up in the report as a negative match: did not find required class.
