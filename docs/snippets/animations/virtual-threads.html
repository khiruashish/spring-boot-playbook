Animated walkthroughVirtual threads — six requests on two carrier threads, and what pinning does

1 · Block, unmount, remount

  1. Six requests, six virtual threads, but only two carrier threads: a ForkJoinPool sized to the CPU count. VT1 and VT2 are mounted and running.
  2. Both make a blocking JDBC call. On a virtual thread, that doesn't block the carrier…
  3. …the JVM unmounts VT1 and VT2 (their stacks are parked on the heap) and mounts VT3 and VT4 on the freed carriers.
  4. They block too and unmount, and VT5 and VT6 run. Six requests are in flight on two OS threads.
  5. When VT1's and VT2's results arrive they remount on whichever carrier is free, not necessarily the one they started on, and carry on where they left off.
  6. So virtual threads make blocking code scale; they don't make CPU work faster. The database pool is still bounded, which is why §5.4 adds a bulkhead.

2 · A pinned carrier

  1. Same pool. This time VT1 calls into a native library through JNI, and the native code blocks.
  2. A virtual thread can't unmount while a native frame is on its stack: it is pinned, and carrier 1 is blocked for the whole call.
  3. Carrier 2 still works normally: VT2 unmounts on its I/O and VT3 takes its place.
  4. But half the pool is gone. Pin both carriers and every virtual thread in the application waits, including ones that have nothing to do with the native call.
  5. On Java 21–23, synchronized around I/O pinned the same way; JDK 24 removed that (JEP 491). Find what's left with JFR jdk.VirtualThreadPinned events (§5.5).
