Animated walkthroughCache stampede — a hot key expires, and two ways to stop the herd

1 · The stampede

  1. Five concurrent requests ask for the price of ATTA-5KG. The key is fresh…
  2. …so all five are cache hits, answered in about a millisecond. The database isn't touched.
  3. The 120-second TTL runs out.
  4. The next five requests arrive in the same instant, and every one of them misses…
  5. …so all five run the same expensive query. At hundreds of requests per second, one hot key expiring can flatten the database: the thundering herd.
  6. Five identical results come back and the same key is written five times. Four of those queries were wasted.

2 · One loader per key

  1. Same expiry, but the method is now @Cacheable(sync = true).
  2. All five misses meet a per-key lock. The first caller loads the value; the other four wait for its result instead of querying.
  3. Exactly one query reaches the database.
  4. The loader stores the value in the cache and releases the lock…
  5. …and all five requests get the same value. Note that sync = true locks inside one JVM (Caffeine); across pods with Redis you need a locking cache writer, a distributed lock, or stale-while-revalidate.

3 · Many keys, one TTL

  1. A different herd: after a deploy, warm-up writes 10,000 prices at once, all with exactly 120 s TTL.
  2. Two minutes later they all expire in the same second. It's a stampede across keys, not just on one.
  3. Fix: jitter. With TTL = 120 s ± 20 s (§5.4), expiries spread over 40 seconds…
  4. …so the database sees a steady trickle of reloads instead of a spike.
