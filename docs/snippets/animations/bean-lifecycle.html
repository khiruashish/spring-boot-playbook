Animated walkthroughA singleton's life — from BeanDefinition to proxy to @PreDestroy

1 · Startup

  1. During refresh(), the container reads OrderService's BeanDefinition and calls the constructor. Constructor-injected dependencies (OrderRepository, PricingService) are created first, so they exist before the object does.
  2. populateBean() fills @Autowired fields and setters. With constructor injection there's nothing left to do here, which is one reason constructor injection is the default.
  3. Aware callbacks: setBeanName("orderService"), then BeanClassLoaderAware and BeanFactoryAware. The context-level ones (ApplicationContextAware, EnvironmentAware …) arrive in the next step through a post-processor.
  4. Every BeanPostProcessor gets postProcessBeforeInitialization. CommonAnnotationBeanPostProcessor calls your @PostConstruct method here. Note the side panel: there is still no proxy.
  5. InitializingBean.afterPropertiesSet() runs next. It's a Spring interface, so application code should prefer @PostConstruct.
  6. Then the custom init method from @Bean(initMethod = "…"), which is how you hook third-party classes you can't annotate. Order: @PostConstruct → afterPropertiesSet() → initMethod.
  7. postProcessAfterInitialization: AnnotationAwareAspectJAutoProxyCreator sees @Transactional (or any aspect) and returns a proxy wrapping the object. From here on, the proxy is the bean.
  8. The proxy goes into the singleton cache, so every injection point and getBean() gets the proxy, never the raw object. Once all singletons are ready: SmartInitializingSingleton, SmartLifecycle.start(), then ContextRefreshedEvent.

2 · Shutdown

  1. context.close() (or SIGTERM with graceful shutdown) publishes ContextClosedEvent, then stops SmartLifecycle beans in reverse phase order. In-flight work drains before any bean is destroyed.
  2. @PreDestroy runs first. It's the default choice for cleanup: close pools, flush buffers.
  3. Then DisposableBean.destroy(), the Spring-interface equivalent.
  4. Finally the destroy method. For @Bean methods it's inferred: a public close() or shutdown() is called automatically. Prototype beans never reach this row; whoever asked for them owns their cleanup.

3 · Trap: @Transactional work in @PostConstruct

  1. Same startup, but now OrderService has @PostConstruct void warmUp() { loadPrices(); }, and loadPrices() is @Transactional.
  2. @PostConstruct runs on the raw object, before any proxy exists. loadPrices() runs with no transaction: no rollback, no readOnly, and lazy associations can throw LazyInitializationException. Often nothing fails at startup; the work just silently isn't transactional.
  3. The proxy is only created at BPP · after, three steps later, which is too late for anything @PostConstruct already did.
  4. Refresh finishes and the proxy is in the cache. Other beans now see the transactional version.
  5. Fix: move warm-up to an ApplicationRunner or an @EventListener(ApplicationReadyEvent.class) that calls orderService.loadPrices(). It runs after refresh, through the proxy, so @Transactional applies. To keep traffic away until warm-up ends, hold back readiness (§6.2).
