    8. Write a Custom Auto-Configuration (Starter)¶

    L3 ★★★ · @AutoConfiguration, @ConditionalOnMissingBean, @ConditionalOnProperty, ApplicationContextRunner

    Problem¶

    Package a reusable GreetingService as a Spring Boot starter. It must be on by default, configurable via greeting.prefix, switchable off via greeting.enabled=false, and it must back off when the application defines its own bean. Test every scenario in milliseconds.

    Key idea¶

    An auto-configuration is a @AutoConfiguration class listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. Conditions decide whether it applies: @ConditionalOnProperty for the switch and @ConditionalOnMissingBean so user beans win. ApplicationContextRunner starts tiny contexts per scenario without booting the whole application.

    flowchart TD S[context starts] --> I["read AutoConfiguration.imports"] I --> P{"greeting.enabled != false?"} P -->|no| X[skip whole class] P -->|yes| M{"user GreetingService bean exists?"} M -->|yes| B[back off: user bean wins] M -->|no| C["create default bean (prefix from GreetingProperties)"]

    Solution¶

    GreetingAutoConfiguration.java
    package com.playbook.interview.p08;

import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;

/**
 * Problem 8: a custom auto-configuration. Registered in
 * META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, which also keeps it out of component scanning.
 */
@AutoConfiguration
@ConditionalOnProperty(prefix = "greeting", name = "enabled", havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(GreetingProperties.class)
public class GreetingAutoConfiguration {

    /** Back off if the application defines its own GreetingService: user beans always win. */
    @Bean
    @ConditionalOnMissingBean
    GreetingService greetingService(GreetingProperties props) {
        return name -> props.prefix() + ", " + name + "!";
    }
}
    GreetingProperties.java
    package com.playbook.interview.p08;

import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties("greeting")
public record GreetingProperties(String prefix, boolean enabled) {
    public GreetingProperties {
        if (prefix == null) prefix = "Hello";
    }
}
    org.springframework.boot.autoconfigure.AutoConfiguration.imports
    com.playbook.interview.p08.GreetingAutoConfiguration
    GreetingAutoConfigurationTest.java
    package com.playbook.interview.p08;

import org.junit.jupiter.api.Test;
import org.springframework.boot.autoconfigure.AutoConfigurations;
import org.springframework.boot.test.context.runner.ApplicationContextRunner;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import static org.assertj.core.api.Assertions.assertThat;

/** ApplicationContextRunner: start tiny contexts in milliseconds, one per scenario. */
class GreetingAutoConfigurationTest {

    private final ApplicationContextRunner runner = new ApplicationContextRunner()
            .withConfiguration(AutoConfigurations.of(GreetingAutoConfiguration.class));

    @Test
    void createsDefaultBean() {
        runner.run(ctx -> assertThat(ctx.getBean(GreetingService.class).greet("Ana")).isEqualTo("Hello, Ana!"));
    }

    @Test
    void bindsProperties() {
        runner.withPropertyValues("greeting.prefix=Namaste")
              .run(ctx -> assertThat(ctx.getBean(GreetingService.class).greet("Ana")).isEqualTo("Namaste, Ana!"));
    }

    @Test
    void backsOffWhenUserDefinesTheirOwnBean() {
        runner.withUserConfiguration(CustomGreeting.class)
              .run(ctx -> {
                  assertThat(ctx).hasSingleBean(GreetingService.class);
                  assertThat(ctx.getBean(GreetingService.class).greet("Ana")).isEqualTo("Hi Ana (custom)");
              });
    }

    @Test
    void canBeSwitchedOff() {
        runner.withPropertyValues("greeting.enabled=false").run(ctx -> assertThat(ctx).doesNotHaveBean(GreetingService.class));
    }

    @Configuration
    static class CustomGreeting {
        @Bean GreetingService custom() { return name -> "Hi " + name + " (custom)"; }
    }
}

    Walkthrough¶

    Code Why
    @ConditionalOnProperty(prefix = "greeting", name = "enabled", havingValue = "true", matchIfMissing = true) On by default (matchIfMissing) and off with one property.
    @Bean @ConditionalOnMissingBean GreetingService greetingService(...) The core contract of a good starter: never override what the user defined. Auto-configurations are processed after user configuration, which is what makes this condition reliable.
    AutoConfiguration.imports file Registration replaces the old spring.factories key. Classes listed here are also excluded from component scanning, so the conditions aren't bypassed.
    new ApplicationContextRunner().withConfiguration(AutoConfigurations.of(...)) Each test builds a context with exactly the configuration, user beans and properties it needs, then asserts with assertThat(ctx).hasSingleBean(...).

    Complexity¶

    Approach Time Space
    context startup per test milliseconds tiny context

    Run it¶

    cd coding-interview && mvn -q test -Dtest=GreetingAutoConfigurationTest

    GreetingAutoConfigurationTest: 4 tests, 0 failures
  ✔ backs off when user defines their own bean
  ✔ binds properties
  ✔ can be switched off
  ✔ creates default bean

    Common mistakes¶

    • Putting @ConditionalOnMissingBean on a bean in a regular @Configuration class. Ordering isn't guaranteed there, so the condition may be evaluated before the user's bean is registered.
    • Letting component scanning pick up the auto-configuration package, which bypasses the conditions.
    • Starters that pull in heavy dependencies unconditionally. Use @ConditionalOnClass together with optional dependencies.

    Follow-up questions¶

    How do you debug why an auto-configuration did or didn't apply?

    Run with --debug or debug=true to print the condition evaluation report, or call the Actuator /actuator/conditions endpoint. In tests, ApplicationContextRunner failures include the report.

    How do you order auto-configurations?

    Use @AutoConfiguration(after = DataSourceAutoConfiguration.class) (or before). Don't use @Order for this; it doesn't order auto-configuration classes.
