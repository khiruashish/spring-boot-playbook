    7. @Transactional: The Three Traps¶

    L3 ★★★ · Rollback rules, self-invocation, REQUIRES_NEW audit

    Problem¶

    A money transfer debits one account and credits another. Prove with tests: (1) a checked exception doesn't roll back by default; (2) calling a @Transactional method on this doesn't start a transaction; (3) an audit row written with REQUIRES_NEW survives the outer rollback.

    Key idea¶

    @Transactional is applied by a proxy around the bean. Three consequences follow. Rollback happens only for unchecked exceptions unless you set rollbackFor. Calls from inside the bean skip the proxy, so they get no transaction. Propagation decides whether an inner call joins the caller's transaction (REQUIRED) or suspends it and commits on its own (REQUIRES_NEW).

    sequenceDiagram participant T as test participant P as TransferService proxy participant S as TransferService (target) participant A as AuditService proxy T->>P: transferWithAudit() P->>P: BEGIN tx1 P->>S: invoke S->>A: record() → suspend tx1, BEGIN tx2, INSERT, COMMIT tx2 S->>S: debit, then throw P->>P: ROLLBACK tx1 (debit undone, audit kept) T->>P: selfInvocationHasTransaction() P->>S: (no tx) S->>S: this.insideTransactional(): proxy bypassed → false

    The same three ideas, animated. Scene 2 is trap 2 (self-invocation), and scene 3 is trap 3 (REQUIRES_NEW audit):

    Animated walkthroughThe @Transactional proxy — and how this.method() escapes it

    1 · Through the proxy

    1. Spring injected a proxy, not your class. The caller's transferService.transfer() lands in the proxy first.
    2. TransactionInterceptor finds @Transactional on transfer() and asks the PlatformTransactionManager for a transaction: BEGIN tx1, with the connection bound to the current thread.
    3. proceed() calls the real transfer() on the target object. The debit and the credit run on tx1's connection.
    4. The method returns normally, so the interceptor commits tx1 on the way out. An unchecked exception would have rolled it back instead.

    2 · The self-invocation trap

    1. Same entry through the proxy. This time transfer() also calls this.audit(), which is annotated @Transactional(REQUIRES_NEW).
    2. The interceptor begins tx1 and calls the real transfer().
    3. this.audit() is a plain Java call on the target object. It never leaves the bean, so no interceptor runs: the dashed route back through the proxy never happens. REQUIRES_NEW is ignored and the audit row is written inside tx1.
    4. Back in transfer(), the debit finds insufficient funds and throws a RuntimeException.
    5. The interceptor sees the exception and rolls back tx1. The audit row disappears along with the debit, which is the opposite of what REQUIRES_NEW promised.

    3 · The fix: call another bean

    1. Move the audit logic into its own bean, AuditService.record(), and inject it into TransferService. (A self-injected proxy or a TransactionTemplate also work, but a separate bean is the clearest.)
    2. The interceptor begins tx1 and calls the real transfer().
    3. auditService.record() targets a different bean, so the call goes through its proxy. REQUIRES_NEW now takes effect: tx1 is suspended and tx2 begins on a separate connection.
    4. record() inserts the audit row inside tx2.
    5. On return, the audit proxy commits tx2 and resumes tx1. The audit row is now durable.
    6. transfer() throws, and tx1 rolls back the debit. The audit row survives because tx2 already committed. This is exactly what the REQUIRES_NEW test in Interview Problem 7 asserts.

    Solution¶

    TransferService.java
    package com.playbook.interview.p07;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.support.TransactionSynchronizationManager;

/** Problem 7: the three @Transactional traps: checked exceptions, self-invocation, and REQUIRES_NEW for audit logs. */
@Service
public class TransferService {

    public static class InsufficientFundsException extends Exception {          // CHECKED on purpose
        public InsufficientFundsException(String m) { super(m); }
    }

    private final JdbcTemplate jdbc;
    private final AuditService audit;

    TransferService(JdbcTemplate jdbc, AuditService audit) { this.jdbc = jdbc; this.audit = audit; }

    /** TRAP 1: by default only RuntimeException/Error roll back. A checked exception COMMITS the debit. */
    @Transactional
    public void transferDefaultRollback(String from, String to, long cents) throws InsufficientFundsException {
        debitThenCredit(from, to, cents);
    }

    /** FIX 1: declare rollbackFor (or throw unchecked domain exceptions). */
    @Transactional(rollbackFor = InsufficientFundsException.class)
    public void transferWithRollbackFor(String from, String to, long cents) throws InsufficientFundsException {
        debitThenCredit(from, to, cents);
    }

    /** TRAP 2: calling an annotated method on `this` bypasses the proxy, so NO transaction starts. */
    public boolean selfInvocationHasTransaction() { return this.insideTransactional(); }

    @Transactional
    public boolean insideTransactional() { return TransactionSynchronizationManager.isActualTransactionActive(); }

    /** FIX 3 / REQUIRES_NEW: the audit row survives even though the outer transfer rolls back. */
    @Transactional
    public void transferWithAudit(String from, String to, long cents) {
        audit.record("attempt " + from + "->" + to + " " + cents);           // another bean -> goes through its proxy
        jdbc.update("UPDATE account SET balance = balance - ? WHERE id = ?", cents, from);
        throw new IllegalStateException("fraud check failed");               // rolls back the debit, not the audit
    }

    private void debitThenCredit(String from, String to, long cents) throws InsufficientFundsException {
        jdbc.update("UPDATE account SET balance = balance - ? WHERE id = ?", cents, from);
        Long balance = jdbc.queryForObject("SELECT balance FROM account WHERE id = ?", Long.class, from);
        if (balance < 0) throw new InsufficientFundsException(from + " would go to " + balance);
        jdbc.update("UPDATE account SET balance = balance + ? WHERE id = ?", cents, to);
    }

    @Service
    public static class AuditService {
        private final JdbcTemplate jdbc;
        AuditService(JdbcTemplate jdbc) { this.jdbc = jdbc; }

        @Transactional(propagation = Propagation.REQUIRES_NEW)               // suspends the caller's tx, commits on its own
        public void record(String message) { jdbc.update("INSERT INTO audit_log(message) VALUES (?)", message); }
    }
}
    TransferServiceTest.java
    package com.playbook.interview.p07;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.jdbc.core.JdbcTemplate;

import static org.assertj.core.api.Assertions.*;

@SpringBootTest
class TransferServiceTest {

    @Autowired TransferService service;
    @Autowired JdbcTemplate jdbc;

    @BeforeEach
    void reset() {
        jdbc.update("DELETE FROM account");
        jdbc.update("DELETE FROM audit_log");
        jdbc.update("INSERT INTO account VALUES ('ana', 1000), ('bob', 0)");
    }

    long balance(String id) { return jdbc.queryForObject("SELECT balance FROM account WHERE id = ?", Long.class, id); }

    @Test
    void trap1_checkedException_commitsTheDebit_byDefault() {
        assertThatThrownBy(() -> service.transferDefaultRollback("ana", "bob", 5_000)).isInstanceOf(TransferService.InsufficientFundsException.class);
        assertThat(balance("ana")).isEqualTo(-4_000);           // money destroyed: the debit was COMMITTED
    }

    @Test
    void fix1_rollbackFor_rollsBackOnCheckedException() {
        assertThatThrownBy(() -> service.transferWithRollbackFor("ana", "bob", 5_000)).isInstanceOf(TransferService.InsufficientFundsException.class);
        assertThat(balance("ana")).isEqualTo(1_000);
    }

    @Test
    void trap2_selfInvocation_bypassesTheProxy() {
        assertThat(service.insideTransactional()).isTrue();      // called through the proxy
        assertThat(service.selfInvocationHasTransaction()).isFalse();  // called via `this`: no transaction
    }

    @Test
    void requiresNew_auditSurvivesOuterRollback() {
        assertThatThrownBy(() -> service.transferWithAudit("ana", "bob", 300)).isInstanceOf(IllegalStateException.class);
        assertThat(balance("ana")).isEqualTo(1_000);             // outer tx rolled back
        assertThat(jdbc.queryForObject("SELECT COUNT(*) FROM audit_log", Integer.class)).isEqualTo(1);   // inner tx committed
    }

    @Test
    void happyPath_movesMoney() throws Exception {
        service.transferWithRollbackFor("ana", "bob", 400);
        assertThat(balance("ana")).isEqualTo(600);
        assertThat(balance("bob")).isEqualTo(400);
    }
}

    Walkthrough¶

    Code Why
    @Transactional public void transferDefaultRollback(...) throws InsufficientFundsException The trap. The checked exception propagates but the transaction commits, and the test shows ana at −4000.
    @Transactional(rollbackFor = InsufficientFundsException.class) The fix. Another option is to make domain exceptions extend RuntimeException.
    return this.insideTransactional(); Self-invocation calls the target directly, so the annotation is ignored. isActualTransactionActive() returns false.
    @Transactional(propagation = Propagation.REQUIRES_NEW) public void record(...) Lives in a separate bean (AuditService) so the call goes through a proxy. It commits independently of the caller.
    @BeforeEach reset() with DELETE/INSERT Tests share one H2 database, so each one resets its rows. @Transactional on the test would roll back automatically, but it would also hide trap 1.

    Common mistakes¶

    • Putting @Transactional on private methods or calling annotated methods via this. Neither goes through the proxy.
    • Catching an exception inside the transactional method and swallowing it. The transaction then commits partial work. And if an inner REQUIRED call already marked the transaction rollback-only, the commit fails with UnexpectedRollbackException.
    • Long transactions that include HTTP calls, which hold DB connections and locks while waiting on the network.
    • Annotating controllers. Transaction boundaries belong on application or service methods.

    Follow-up questions¶

    REQUIRED vs REQUIRES_NEW vs NESTED?

    REQUIRED joins an existing transaction or starts one, so everything commits or rolls back together. REQUIRES_NEW suspends the caller's transaction and runs its own, which uses a second DB connection, so watch pool size. NESTED uses a savepoint inside the same transaction: an inner rollback undoes only the inner work. It needs JDBC savepoint support.

    Does readOnly = true do anything?

    Yes. It hints the driver (some route reads to replicas), lets Hibernate skip dirty checking and flushing, and documents intent. It isn't a security boundary: writes may still succeed, depending on the database.
